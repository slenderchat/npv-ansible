# npv-ansible

[English](README.md) | **Русский**

Конфигурация Ansible для хостов сервиса npv на Debian 13.

## Текущее состояние

Сейчас репозиторий содержит:

- статический инвентарь: [`inventory/hosts.yml`](inventory/hosts.yml) и переменные ролей в [`inventory/group_vars`](inventory/group_vars);
- роль `timezone`: [`roles/timezone`](roles/timezone);
- роль `hosts`: [`roles/hosts`](roles/hosts);
- роль `hostname`: [`roles/hostname`](roles/hostname);
- роль `dns_resolver`: [`roles/dns_resolver`](roles/dns_resolver);
- роль `locale`: [`roles/locale`](roles/locale);
- роль `chrony`: [`roles/chrony`](roles/chrony);
- роль `apt_sources`: [`roles/apt_sources`](roles/apt_sources);
- роль `unattended_upgrades`: [`roles/unattended_upgrades`](roles/unattended_upgrades);
- роль `admin_packages`: [`roles/admin_packages`](roles/admin_packages);
- роль `ssh_authorized_keys`: [`roles/ssh_authorized_keys`](roles/ssh_authorized_keys);
- роль `sshd`: [`roles/sshd`](roles/sshd);
- требования к коллекциям: [`collections/requirements.yml`](collections/requirements.yml).

Группы хостов:

- `ingress` — входные узлы сервиса npv.
- `egress` — выходные узлы сервиса npv.

Общие для всех хостов параметры подключения заданы в `all.vars`.

Соглашение об инвентаре: переменные подключения, например `ansible_user`, `ansible_host` и `ansible_port`, могут оставаться в `inventory/hosts.yml`. Переменные ролей для группы хранятся в `inventory/group_vars/<group_name>/<role_name>.yml`, а для отдельного хоста — в `inventory/host_vars/<inventory_hostname>/<role_name>.yml`, где имя каталога точно совпадает с именем хоста в инвентаре, например `ingress-ru-tweb-msk1-01.sl-chat.ru`.

Чтобы просмотреть инвентарь локально:

```sh
ansible-inventory -i inventory/hosts.yml --graph
```

## Коллекции

Установите нужные коллекции на управляющей машине:

```sh
ansible-galaxy collection install -r collections/requirements.yml
```

## Роли

### `timezone`

Устанавливает на управляемом хосте системный часовой пояс `Europe/Moscow` с помощью `community.general.timezone` только с параметром `name`. Аппаратные часы и NTP эта роль не настраивает.

На хостах с systemd модуль читает и задаёт часовой пояс через `timedatectl`, поэтому на управляемом хосте нужны работающий `timedatectl` и файл зоны `/usr/share/zoneinfo/Europe/Moscow` из пакета `tzdata`. `hwclock` (пакет `util-linux-extra`) нужен, только если модуль переходит на путь без systemd, потому что `timedatectl` отсутствует или не работает.

Документированное поведение модуля:

- если на хосте уже задан `Europe/Moscow`, задача не сообщает об изменениях, в том числе с `--check`;
- с `--check` другой часовой пояс отображается как изменение, а на хосте ничего не меняется;
- с `--diff`, отдельно или вместе с `--check`, модуль показывает собственные значения `name` до и после.

### `hosts`

Формирует весь `/etc/hosts` из шаблона (владелец `root:root`, права `0644`) и держит его неизменяемым (`chattr +i`) между запусками. Любые строки, добавленные вне шаблона, например провайдером, удаляются. Системное имя хоста, настройки DNS-резолвера и cloud-init эта роль не настраивает.

Управляемые записи:

- `127.0.0.1 localhost`;
- `127.0.1.1 <short-name> <fqdn>`, где `<fqdn>` — это `inventory_hostname`, а `<short-name>` — его первая метка; текущее системное имя хоста, сетевые факты и DNS не используются;
- стандартные для Debian записи IPv6: `::1 localhost ip6-localhost ip6-loopback`, `ff02::1 ip6-allnodes`, `ff02::2 ip6-allrouters`;
- необязательные записи из `hosts_extra_records` (по умолчанию `[]`), которые выводятся после стандартных в заданном порядке:

  ```yaml
  hosts_extra_records:
    - address: 192.0.2.10
      names:
        - example-01.example.org
        - example-01
  ```

Поведение:

- `/etc/hosts` должен отсутствовать или быть обычным файлом; при любом другом типе, например символьной ссылке, роль завершается ошибкой до любых изменений. Для существующего файла роль читает флаги через `lsattr` при каждом запуске, в том числе на уже сведённом хосте; сведённый запуск не сообщает об изменениях и не выполняет ни перезаписи, ни `chattr`.
- Если нужно обновление, роль временно снимает `i`, если он установлен. Изменения содержимого выполняются атомарной заменой; владелец, группа и права исправляются без замены файла. Если не хватает только `i`, он устанавливается без перезаписи файла.
- После установки `i` роль повторно читает флаги и завершается ошибкой, если `i` нет. Если обновление не удалось после снятия `i`, роль пытается вернуть `i` и сообщает исходную ошибку вместе с результатом проверки.

На управляемом хосте нужны `lsattr` и `chattr` (пакет `e2fsprogs`) и файловая система с поддержкой атрибута immutable. Пока установлен `i`, обычная запись в `/etc/hosts`, в том числе со стороны cloud-init или агентов провайдера, заблокирована.

Проверка и diff:

- с `--check` роль проверяет текущее состояние и прогнозирует изменения, не изменяя `/etc/hosts` и его атрибуты;
- с `--diff` расхождение содержимого даёт один diff содержимого до и после; изменение только атрибута не даёт diff содержимого.

### `hostname`

Задаёт системное имя хоста с помощью `ansible.builtin.hostname` со стратегией `systemd`, которая через `hostnamectl` устанавливает статическое и временное (transient) имя хоста.

Имя хоста — это первая метка FQDN из инвентаря, `inventory_hostname_short`; например, `ingress-ru-tweb-msk1-01.sl-chat.ru` получает имя `ingress-ru-tweb-msk1-01`. Файлом `/etc/hosts` управляет роль `hosts`, а не эта роль.

Режимы проверки и diff поддерживаются модулем нативно: с `--check` другое имя хоста отображается как изменение без изменения хоста, а с `--diff` модуль показывает имя хоста до и после.

### `dns_resolver`

Направляет разрешение имён приложений через локальный stub systemd-resolved на `127.0.0.53`. Публичный DNS уходит только на DNS-over-TLS-серверы группы хоста. networkd, netplan, cloud-init и состояние интерфейсов роль не меняет.

Серверы задаются упорядоченным списком в обязательной групповой переменной `dns_resolver_upstreams`. Каждый элемент записывается в синтаксисе systemd-resolved: `IPv4:порт#tls-имя`. Порт 53 запрещён: systemd-resolved хранит и 53, и 853 как порт 0, а при строгом DNS-over-TLS это означает 853. Значения по умолчанию нет: если список не задан или записан неверно, роль завершается ошибкой до любых изменений. Значения заданы в `inventory/group_vars/ingress/dns_resolver.yml` и `inventory/group_vars/egress/dns_resolver.yml`:

| Группа | `dns_resolver_upstreams` |
| --- | --- |
| `ingress` | `77.88.8.88:853#safe.dot.dns.yandex.net`, `77.88.8.2:853#safe.dot.dns.yandex.net`, `185.191.32.7:853#public.sdns.bi.zone`, `185.191.32.8:853#public.sdns.bi.zone` |
| `egress` | `9.9.9.9:853#dns.quad9.net`, `149.112.112.112:853#dns.quad9.net`, `1.1.1.2:853#security.cloudflare-dns.com`, `1.0.0.2:853#security.cloudflare-dns.com` |

Drop-in `/etc/systemd/resolved.conf.d/50-dns_resolver.conf` сбрасывает унаследованные списки `DNS=` и `Domains=` и задаёт `DNS=<весь список>`, `Domains=~.`, `DNSOverTLS=yes`, `DNSStubListener=yes`, `LLMNR=no` и пустой `FallbackDNS=`. Между серверами списка systemd-resolved переключается сам и не возвращается к первому сразу. Шифрование и проверка сертификата строгие: отката на открытый DNS нет. DNS-серверы, полученные по DHCP, могут оставаться на интерфейсе; пока действует глобальный `~.`, они не используются.

`/etc/resolv.conf` становится обычным файлом `root:root` с правами `0644` и флагом immutable (`chattr +i`). В нём только `nameserver 127.0.0.53`, `options edns0 trust-ad` и `search .`. Прежний файл, символьная ссылка или отсутствующий путь заменяются.

Порядок обычного запуска:

1. Если нет `e2fsprogs` (`lsattr`, `chattr`), сначала установить его, пока работает исходный резолвер; состояние резолвера при этом не меняется. Затем записать исходное состояние: тип `/etc/resolv.conf` (обычный файл, символьная ссылка или отсутствует; любой другой тип — ошибка), его флаг `i` (ошибка `lsattr` останавливает запуск; флаг никогда не считается снятым по умолчанию), содержимое (в том числе через ссылку), drop-in с владельцем, группой и правами, состояние пакетов, а также запущен ли и включён ли systemd-resolved.
2. Установить остальные недостающие пакеты (`systemd-resolved`, `bind9-dnsutils`, `ca-certificates`, без рекомендуемых), пока работает исходный резолвер. При первой установке пакет Debian может заменить незащищённый `/etc/resolv.conf` ссылкой на stub и запустить сервис; после установки путь проверяется заново.
3. Записать drop-in. Если он изменился, перезапустить systemd-resolved; затем убедиться, что сервис включён и запущен. Неизменённый работающий сервис не перезапускается.
4. Прочитать действующие настройки через D-Bus (`busctl`) и завершиться ошибкой с конфликтующим значением и подсказкой, где искать, если публичные запросы могут уйти мимо утверждённого списка. Серверы сравниваются по адресу, порту и TLS-имени в порядке инвентаря; сохранённый порт 0 считается за 853, потому что на том же шаге проверяется `DNSOverTLS=yes`, а любой другой неожиданный порт — расхождение. Например: более поздний drop-in меняет `DNS=`, глобальные домены не равны ровно `~.`, у сетевого интерфейса есть свой DNS-домен, текущий сервер не из списка, `FallbackDNS=` не пуст, либо `DNSOverTLS`, `LLMNR` или `DNSStubListener` отличаются. Если текущим стал любой утверждённый запасной сервер, это не ошибка.
5. Запросить `deb.debian.org.` (тип A) через `dig` напрямую у `127.0.0.53` с ограниченным числом повторов. Если запуск что-то меняет или исправляет, кэш systemd-resolved сначала сбрасывается. На уже сведённом хосте кэш не трогается, поэтому ответ может прийти из кэша. Успех подтверждает настроенный путь разрешения, а не ответ каждого из серверов.
6. Только после этого атомарно заменить `/etc/resolv.conf`, установить `i` и перечитать флаги. Обычный файл заменяется модулем template. В символьную ссылку, в том числе висячую или такую, цель которой уже содержит нужный текст, запись никогда не идёт: полный файл готовится как `/etc/.resolv.conf.dns_resolver.tmp` с `root:root 0644` и переименовывается поверх ссылки; при ошибке промежуточный файл удаляется. На уже сведённом хосте ничего не перезаписывается, `chattr` не выполняется и сервисы не перезапускаются.

Если любой шаг после первого завершился ошибкой, роль восстанавливает то, что отличается от записанного состояния, и затем завершается с исходной ошибкой и результатом каждого шага восстановления:

- drop-in (или удаляет его, если его не было);
- состояние сервиса: перезапуск с восстановленной конфигурацией, если он работал, или остановка, если не работал; для юнита, существовавшего до запуска, также возвращается состояние `enabled` или `disabled`, если запуск его изменил, а другие состояния, например `masked`, не меняются, и ничего не размаскируется. Юнит, установленный этим запуском, остаётся установленным и включённым, и отчёт об этом сообщает;
- исходный обычный файл с владельцем, правами и флагом `i` (замена ссылки идёт тем же переименованием подготовленного файла), исходная ссылка или отсутствие файла.

Каждый восстановленный элемент перечитывается, и восстановленным называется только проверенный результат.

Если исходная ссылка больше не ведёт к исходному содержимому (например, её цель принадлежала резолверу, который удалила установка пакета, или это файл systemd-resolved при остановленном сервисе), сохранённое содержимое заменяет ссылку обычным файлом через то же переименование подготовленного файла, и роль сообщает об этом. После восстановления роль один раз проверяет разрешение имён через NSS (`getent`). Пакеты никогда не удаляются.

Проверка и diff:

- с `--check` роль читает текущее состояние и прогнозирует установку пакетов, каталог и файл drop-in, перезапуск или запуск сервиса, замену ссылки обычным файлом и флаг `i`. Без `lsattr` прогнозируется установка необходимого пакета, а текущий флаг `i` обычного `/etc/resolv.conf` сообщается как неизвестный; только из-за этого запуск не завершается ошибкой. Роль не запускает сервисы, не сбрасывает кэш и не отправляет DNS-запросы, а проверку во время выполнения помечает как отложенную. На хосте без пакета установка и запуск показываются сообщениями, потому что apt не может обновить списки пакетов, а юнита ещё нет.
- с `--diff` для drop-in и `/etc/resolv.conf` показывается по одному diff содержимого; для ссылки «до» — это содержимое её цели, для висячей ссылки — пустое содержимое.

### `locale`

Задаёт постоянную системную локаль по умолчанию `LANG=C.UTF-8` в `/etc/locale.conf` одной задачей `ansible.builtin.lineinfile`. Если файла нет, он создаётся; владелец и права поддерживаются как `root:root 0644`. Существующая активная строка `LANG=`, в кавычках или без, заменяется; `LANGUAGE`, `LC_*` и закомментированные строки, а также другие настройки и комментарии сохраняются. Генерация локалей и уже запущенные сессии этой ролью не затрагиваются.

Режимы проверки и diff поддерживаются модулем нативно: с `--check` отсутствующий или другой `LANG` отображается как изменение без изменения хоста, а с `--diff` модуль показывает содержимое файла до и после.

### `chrony`

Обеспечивает установку пакета `chrony` и включение и запуск `chrony.service` модулями `ansible.builtin.apt` и `ansible.builtin.systemd_service`. Конфигурация пакета и источники времени сохраняются; повторный запуск не сообщает об изменениях и не перезапускает сервис. Работающий демон сам по себе не подтверждает синхронизацию часов.

С `--check` роль читает только локальные метаданные APT и не обновляет их: если chrony уже установлен или в них есть кандидат на установку, apt моделирует установку и с `--diff` показывает транзакцию пакетов; иначе установка отображается как изменение, транзакция которого неизвестна, пока метаданные APT недоступны. Если `chrony.service` ещё нет, запланированный запуск показывается сообщением; существующий юнит оценивается модулем.

### `apt_sources`

Управляет источниками APT Debian в `/etc/apt/sources.list.d/debian.sources` (deb822, `root:root 0644`): `https://deb.debian.org/debian` для `trixie` и `trixie-updates` и `https://security.debian.org/debian-security` для `trixie-security`, с `Types: deb` и `Signed-By: /usr/share/keyrings/debian-archive-keyring.pgp` в каждой записи. До любых изменений связка ключей и набор сертификатов `/etc/ssl/certs/ca-certificates.crt` должны быть доступны для чтения; ключи никогда не загружаются. Роль не устанавливает, не обновляет и не удаляет пакеты и не задаёт ни `APT::Default-Release`, ни записи `deb-src`.

Переменные (по умолчанию `main` и без backports):

- `apt_sources_components` — полный упорядоченный список компонентов, уникальные значения из `main`, `contrib`, `non-free` и `non-free-firmware`;
- `apt_sources_backports_packages` — точные имена бинарных пакетов, разрешённых из `trixie-backports`; пустой список отключает backports.

Переопределения задаются в `inventory/group_vars/<group_name>/apt_sources.yml` или `inventory/host_vars/<inventory_hostname>/apt_sources.yml`. Пример файла хоста:

```yaml
apt_sources_components:
  - main
  - non-free-firmware
apt_sources_backports_packages:
  - example-package
```

При непустом списке роль добавляет запись `trixie-backports` и `/etc/apt/preferences.d/npv-backports.pref`, который даёт перечисленным пакетам приоритет 100, а всем остальным пакетам backports — приоритет -1, поэтому обычным источником остаётся stable везде, где в нём есть пакет. Добавление пакета в список ничего не устанавливает и не обновляет. Предполагаемый порядок работы — явный выбор, `apt install <package>/trixie-backports`; зависимость, которой нужна версия из backports, тоже должна быть в списке. Это соглашение, а не гарантия APT: пакет из списка без кандидата в stable устанавливается из backports обычной командой `apt install`. Файл предпочтений записывается до включения источника и удаляется только после его отключения.

Миграция. До любых изменений роль читает `/etc/apt/sources.list`, активные файлы `.list` и `.sources` и предпочтения APT, не обращаясь к зеркалам. Распознаются только простые записи `deb`/`deb-src` для `/debian` на `deb.debian.org`, `ftp.debian.org` или `ftp.<cc>.debian.org` и для `security.debian.org/debian-security` с перечисленными выше выпусками trixie, компонентами Debian и не более чем `signed-by` со связкой ключей Debian. Файл только с такими записями, активными или отключёнными, мигрируется: в `/etc/apt/sources.list` остаётся комментарий, другой файл удаляется, официальные записи `deb-src` отбрасываются. Другие репозитории и предпочтения не затрагиваются. Роль останавливается до любых изменений, называя файл и причину, если перезаписываемый или удаляемый файл, включая существующий `debian.sources`, содержит также другие записи или отключённые записи deb822 других репозиториев, у официальной записи другой выпуск или дополнительные параметры, backports берётся из другого архива, `npv-backports.pref` записан не ролью или маркер незавершённого обновления не является собственным обычным файлом роли. При включённых backports запись предпочтений сохраняется, только если она заведомо не может совпасть с `trixie-backports`: закрепление `origin` для узла, отличного от `deb.debian.org`, или закрепление `release` с буквальным значением `n`, отличным от `trixie-backports`, или буквальным значением `o` или `l`, отличным от `Debian Backports`. Значение выпуска (`a=`) никогда не считается доказательством, поскольку псевдонимы выпусков переходят между релизами. Любая другая запись, например закрепление `version`, останавливает роль с указанием файла и строки; полный язык политик APT роль не вычисляет. При отключённых backports другие предпочтения не проверяются. Другие схемы, включая зеркала провайдеров и URI `mirror+file:`, автоматически не мигрируются; запись с другим URI, выпуском trixie и явным `signed-by` со связкой ключей архива Debian считается зеркалом Debian и останавливает роль, а запись без этих признаков считается репозиторием поставщика и сохраняется.

Удаление компонента, сужение или отключение backports проверяется по установленным пакетам в локальном кэше APT (`dpkg-query`, `apt-cache policy`). Для каждого установленного пакета, версия которого есть в удаляемом источнике или теряет допуск backports, и для каждой установленной версии, известной только из статуса dpkg, оставшийся источник должен предлагать установленную или более новую версию (сравнение `dpkg --compare-versions` на хосте) с приоритетом не ниже 100 после изменения. Версии backports оцениваются с предлагаемым ограничением; остальные приоритеты берутся из текущего `apt-cache policy` и существующих предпочтений, которые роль сохраняет. Роль останавливается до любых изменений с причиной для каждого пакета: недоступен (версию предлагает только удаляемый источник), запрещён (оставшееся предложение ниже приоритета 100), происхождение неясно (версия из статуса dpkg без оставшегося предложения; роль не утверждает, откуда она взялась) или не определено (существующие предпочтения или неоднозначная запись `apt-cache policy` не позволяют определить результат). Она также останавливается, если нет индекса удаляемого источника. Эти проверки выполняются только при удалении компонента или сужении допуска backports; иначе индексы не нужны.

После изменения источников обычный запуск обновляет индексы командой `apt-get update` с `APT::Update::Error-Mode=any`, поэтому частичный сбой завершает запуск ошибкой. `/var/lib/apt/npv-apt-sources.refresh-pending` создаётся до изменения и удаляется после успешного обновления; пока он существует, следующий запуск повторяет обновление. Повторный запуск без изменений ничего не меняет и индексы не обновляет.

Проверка и diff:

- с `--check` роль выполняет ту же проверку только для чтения и останавливается на тех же препятствиях; она перечисляет мигрируемые файлы, показывает удаления и необходимость обновления индексов и ничего не записывает, не обновляет и не обращается к зеркалам. Файл, каталога которого ещё нет, показывается сообщением;
- с `--diff` `debian.sources`, файл предпочтений и сокращённый `/etc/apt/sources.list` показывают разницу содержимого; для удаляемых файлов показывается состояние пути.

### `unattended_upgrades`

Включает ежедневные автоматические обновления безопасности с помощью пакета `unattended-upgrades` и юнитов `apt-daily.timer` и `apt-daily-upgrade.timer` из пакета `apt`, сохраняя их штатное расписание: индексы обновляются, а автоматические обновления запускаются ежедневно. Политика записывается в `/etc/apt/apt.conf.d/99npv-unattended-upgrades` (`root:root 0644`) до установки пакета. Она сбрасывает унаследованные правила источников, поэтому допускаются только версии пакетов из архива, соответствующего `origin=Debian,codename=trixie-security,label=Debian-Security`; версии из `trixie`, `trixie-updates`, backports или репозиториев поставщиков автоматически не устанавливаются. Источники, закрепления, конфигурация пакетов и прочие настройки, например почта и очистка, не затрагиваются.

Если после автоматического обновления появляется `/var/run/reboot-required`, хост перезагружается немедленно, даже если пользователи подключены по SSH; их сессии разрываются. Сама роль никогда не запускает обновление и не перезагружает хост.

Оба таймера должны существовать; отсутствующий или замаскированный таймер останавливает роль до любых изменений. После установки пакета обычный запуск читает итоговую конфигурацию через `apt-config dump`, включая значения по умолчанию из пакета и файлы, загружаемые после файла роли, и при расхождении завершается ошибкой, называя управляемый параметр и его ожидаемое значение; таймеры включаются и запускаются только после успешной проверки. Уже активные таймеры не останавливаются, поэтому неудачная проверка не отменяет уже запланированные ими задания.

Включённые таймеры и проверенная конфигурация не доказывают, что обновление или перезагрузка действительно произошли. Такие свидетельства — в `/var/log/unattended-upgrades/`, `journalctl -u apt-daily-upgrade.service` и `journalctl --list-boots`.

Проверка и diff: с `--check` ничего не записывается, не обновляется и не запускается, а действующая конфигурация сравнивается, только если файл политики уже актуален; с `--diff` для файла политики показывается разница содержимого. Установка пакета моделируется так же, как для `chrony`.

### `admin_packages`

Устанавливает пакеты для администрирования хоста одной операцией `ansible.builtin.apt` (`state: present`, без рекомендуемых пакетов). Установленные пакеты не обновляются, а удаление имени из списка не удаляет пакет. Редакторы, права на захват трафика и Eternal Terminal этой ролью не настраиваются.

`admin_packages_list` — полный список пакетов. Значение для группы или хоста заменяет значения по умолчанию, а не дополняет их, поэтому переопределение должно повторять все сохраняемые пакеты; пустой список ничего не делает. По умолчанию:

- `iproute2` — `ip` и `ss`;
- `iputils-ping` — `ping`;
- `bind9-dnsutils` — `dig` и `nslookup`;
- `curl`;
- `tcpdump`;
- `htop`;
- `ncdu`;
- `neovim`;
- `hx` — редактор Helix (имя пакета в Debian).

Переопределения задаются в `inventory/group_vars/<group_name>/admin_packages.yml` или `inventory/host_vars/<inventory_hostname>/admin_packages.yml`.

С `--check` роль читает только локальные метаданные APT, не обновляет их и не обращается к зеркалам. apt моделирует установку пакетов, которые уже установлены или имеют в них кандидата на установку, и с `--diff` показывает их транзакцию. Остальные пакеты перечисляются в сообщении, отображаемом как изменение: пока метаданные APT для них недоступны, например на новом хосте с неполными индексами, полную транзакцию определить нельзя.

### `ssh_authorized_keys`

Приводит `/root/.ssh/authorized_keys` (`root:root 0600`, в `/root/.ssh` с `root:root 0700`) к точному списку одобренных ключей. Настройки sshd, порты, пароли, межсетевой экран, fail2ban и Eternal Terminal относятся к другим ролям.

Входные данные:

- `ssh_authorized_keys_list` (обязательна, без значения по умолчанию) — единый список строк открытых ключей для всех хостов в полностью зашифрованном Vault файле `inventory/group_vars/all/ssh_authorized_keys.yml`; для запуска нужен пароль Vault. Поддерживаются только простые ключи: `ssh-ed25519`, `ssh-rsa`, `ecdsa-sha2-nistp256/384/521`, `sk-ssh-ed25519@openssh.com`, `sk-ecdsa-sha2-nistp256@openssh.com`, каждый с необязательным комментарием. Опции ключей, сертификаты, закрытые ключи, пустой или некорректный список, ключи, которые не разбирает `ssh-keygen` на управляющей машине, и повторяющиеся ключи (одинаковые тип и данные ключа при любом комментарии) останавливают роль до любых изменений.
- `ssh_authorized_keys_proof_identity` — путь на управляющей машине к файлу открытого ключа (`*.pub`), ключ которого есть в списке, а закрытый ключ загружен в `ssh-agent` управляющей машины; задаётся при запуске, например `-e ssh_authorized_keys_proof_identity=~/.ssh/id_ed25519.pub`. Нужна только тогда, когда требуется проверка. Закрытые ключи не читаются и не копируются.

Добавление ключей или изменение только комментариев, порядка, повторов или строк-комментариев проверки не требует. Удаление ключа или замена записи с опциями (например, ограничения `command=` от провайдера) требует: если ключа проверки ещё нет в файле, он дописывается в конец без изменения существующих записей; затем управляющая машина выполняет новый вход `ssh` как `root` на `ansible_host` (или имя из инвентаря) через текущий `ansible_port`, предлагая только ключ проверки как простой открытый ключ (алгоритмы подписи сертификатов исключены из стандартного `PubkeyAcceptedAlgorithms`), с `-F none`, без общего соединения, без входа по паролю или keyboard-interactive и со `StrictHostKeyChecking=yes` по стандартным файлам `known_hosts`. Только после успеха файл атомарно заменяется. Если проверка не прошла, запуск завершается ошибкой, в которой указаны только хост, порт, код возврата `ssh`, совпал ли маркер успеха и был ли дописан ключ проверки; вывод `ssh` не показывается. Файл при этом сохраняет все прежние записи без изменений и, если ключа проверки не было, этот одобренный ключ в конце; уже применённые владелец `root:root` и режимы `0700`/`0600` для `/root/.ssh` и файла остаются. Роль останавливается, если для ключа проверки есть запись с опциями. Сошедшийся запуск ничего не записывает и не открывает дополнительных соединений.

Первый запуск: роль не меняет порты. Если хост ещё принимает SSH только на исходном порту, запустите с `-e ansible_port=<port>`; проверка использует то же значение. Проверка игнорирует `ssh_config` и SSH-аргументы Ansible, поэтому ключ хоста уже должен быть в `known_hosts` управляющей машины.

Ограничения: проверка показывает, что root в этот момент может войти с ключом проверки, но не то, что sshd читает именно этот файл (`AuthorizedKeysFile`, `AuthorizedKeysCommand`), и не то, что работают остальные ключи. Итоговый файл после записи повторно не проверяется, а изменение другим процессом между чтением и записью будет перезаписано.

Проверка и diff: с `--check` предсказываются изменения владельца и режима и перезапись файла; ничего не дописывается и проверка входа не выполняется. Ключи, комментарии и содержимое файла никогда не выводятся, в том числе с `--diff`; сообщение показывает число добавляемых и удаляемых ключей, заменяемых записей с опциями, меняются ли только комментарии или порядок и нужна ли проверка.

### `sshd`

Ужесточает настройки сервера OpenSSH и переносит его на порт `22334` одним файлом `/etc/ssh/sshd_config.d/00-npv-sshd.conf` (`root:root 0644`). Ключами по-прежнему управляет роль `ssh_authorized_keys`; fail2ban, Eternal Terminal, межсетевой экран и средства провайдера роль не настраивает.

Действующая политика, проверяемая через `sshd -T`:

- только `Port 22334`;
- только `root` (`AllowUsers root`, `PermitRootLogin prohibit-password`), с `AuthenticationMethods publickey` и простыми ключами только из `/root/.ssh/authorized_keys`: `AuthorizedKeysFile /root/.ssh/authorized_keys` (по умолчанию Debian читает ещё и `authorized_keys2`), `AuthorizedKeysCommand none`, `TrustedUserCAKeys none`, а алгоритмы сертификатов исключены из стандартного `PubkeyAcceptedAlgorithms`; вход по паролю, keyboard-interactive и host-based отключены;
- `DisableForwarding yes` (перенаправление агента, X11, TCP и Unix-сокетов) и `PermitTunnel no`;
- оболочки, PTY (`PermitTTY yes`), выполнение команд и SFTP остаются доступны: `ForceCommand none` и `ChrootDirectory none`, а строка Debian `Subsystem sftp /usr/lib/openssh/sftp-server` в `/etc/ssh/sshd_config` сохраняется и обязательна. Ansible сохраняет обычное выполнение команд и передачу файлов; способ передачи в инвентаре не меняется;
- `UsePAM yes` сохраняет обработку account и session через PAM Debian; остальные настройки, включая криптографические значения по умолчанию, остаются как в пакете.

`/etc/ssh/sshd_config` в Debian начинается с `Include /etc/ssh/sshd_config.d/*.conf`, и файл роли идёт первым по сортировке. Для большинства этих параметров sshd берёт первое прочитанное значение, поэтому последующие файлы и остальной `sshd_config` не могут их изменить; это мог бы сделать блок `Match`, поэтому `Match` отклоняется. `AllowUsers` и `Port` устроены иначе: их значения из всех файлов суммируются. Поэтому роль сравнивает полные действующие наборы из `sshd -T` — каждую строку и каждое значение в строке — и требует, чтобы пользователи были ровно `root`, а порты ровно `22334` (во время переноса — оба порта). `Port` кроме `22334`, `ListenAddress` или `AllowUsers` для другого пользователя в другом файле останавливают роль.

Поддерживаемая конфигурация проверяется до любых изменений (в том числе с `--check`). Каждое препятствие останавливает хост с причиной и, где это применимо, файлом и строкой; ничего не меняется:

- работает пакетный `ssh.service` (вариант Debian 13 по умолчанию): активен и включён, запускает `/usr/sbin/sshd -D $SSHD_OPTS`, а `SSHD_OPTS` не задан ни в `/etc/default/ssh`, ни через `Environment=` юнита; `ssh.socket` выключен и неактивен или замаскирован; других активных SSH-сокетов нет, кроме `sshd-vsock.socket` и `sshd-unix-local.socket` генератора ssh из systemd, которые обслуживают AF_VSOCK и локальный AF_UNIX-сокет через `sshd@.service` с той же конфигурацией;
- первая директива `/etc/ssh/sshd_config` — этот `Include`; ни один другой файл не идёт по сортировке раньше `00-npv-sshd.conf`; вне файла роли нет других `Include`, блоков `Match` (их параметры переопределили бы файл роли для подходящих подключений), `ListenAddress` и `Port`, кроме `22334` (`Port 22334` в другом месте допускается и не дублируется);
- `sshd -t` принимает текущую конфигурацию, а порт, через который подключается Ansible, настроен и прослушивается sshd (перенаправление портов не поддерживается);
- нет незавершённого изменения: нет загруженного юнита `npv-sshd-rollback*`, нет `/etc/ssh/npv-sshd.rollback` и `/run/npv-sshd-rollback.armed`.

Первичная настройка у провайдера. Если строк `Port` нет, неявный порт 22 sshd заменяется строками `Port 22` и `Port 22334` файла роли, а затем одной `Port 22334`. Явный `Port 22` в другом файле, например в drop-in провайдера или в `sshd_config`, файл роли убрать не может, поэтому роль останавливается на задаче «Ensure the drop-in is read first and decides the managed keywords» с файлом и строкой; сам файл она не правит. Чтобы продолжить, оставьте текущий сеанс на порту 22 открытым, закомментируйте только эту строку `Port 22` (других `Port` и `ListenAddress` остаться не должно), убедитесь, что `sshd -t` проходит, а `sshd -T` по-прежнему выводит `port 22` (теперь по умолчанию), и откройте второй вход на порт 22, прежде чем закрыть первый; работающий sshd до reload не меняется. Затем выполните первичную настройку. Заданный вручную в другом месте `Port 22334` допускается как есть.

SFTP. Роль требует строку `Subsystem sftp` в действующей конфигурации и проверяет её входом по SFTP; принимаются и внешний `/usr/lib/openssh/sftp-server` Debian, и `internal-sftp`.

Для изменения дополнительно нужны:

- `ssh_authorized_keys_list` и `ssh_authorized_keys_proof_identity`, как в роли `ssh_authorized_keys` (роль загружает её контракт); ключ проверки одобрен и загружен в `ssh-agent`;
- `/root/.ssh/authorized_keys` — обычный файл владельца `root` с режимом `0600`, содержащий ровно одобренные ключи. Порядок ролей: `ssh_authorized_keys` перед `sshd`, в одном плейбуке и с одним ключом проверки;
- при смене порта — доверие к ключу хоста, описанное ниже;
- `ss` (iproute2) и `systemd-run` на хосте, `ssh`, `sftp` и `ssh-keygen` на управляющей машине.

Проверки с управляющей машины. Каждая проверка — новый процесс `ssh` или `sftp` на управляющей машине с `-F none`, только ключом проверки как простым открытым ключом (алгоритмы сертификатов исключены), `User=root`, `BatchMode`, без общего соединения (`ControlMaster=no`, `ControlPath=none`), без входа по паролю или keyboard-interactive и со `StrictHostKeyChecking=yes` и `UpdateHostKeys=no` только по `~/.ssh/known_hosts`. Соединение Ansible и существующие мастер-соединения не используются. Проверка SFTP выполняет пакетную команду только для чтения `ls /`, которая ничего не загружает и не создаёт. Результат сводится к хосту, порту, коду возврата и совпадению маркера успеха; вывод и ключи не показываются.

Доверие к ключу хоста. Подключение к порту, отличному от 22, ищет в `known_hosts` имя `[адрес]:порт`. Перед сменой порта роль требует, чтобы `~/.ssh/known_hosts` доверял имени `[адрес]:22334` ровно с теми ключами хоста, что и текущему имени (`адрес` для порта 22), без пометок `@cert-authority` и `@revoked`. Ничего не принимается при первом подключении, `ssh-keyscan` не используется. После того как отпечаток для порта 22 проверен, скопируйте доверенные записи под новым именем:

```sh
host=46.149.69.224
ssh-keygen -F "$host" -f ~/.ssh/known_hosts
ssh-keygen -F "$host" -f ~/.ssh/known_hosts \
  | awk -v name="[$host]:22334" '!/^[#@]/ { $1 = name; print }' \
  >> ~/.ssh/known_hosts
```

Эта же запись позволяет следующему запуску Ansible на порту `22334` проверить хост.

Первичная настройка нового хоста, доступного на порту 22, — по одному хосту. Плейбуков в репозитории пока нет; используйте собственный плейбук, применяющий `ssh_authorized_keys`, а затем `sshd`, причём `sshd` последней:

```sh
ansible-playbook -i inventory/hosts.yml <your-play>.yml --limit <host> \
  -e ansible_port=22 \
  -e ssh_authorized_keys_proof_identity=~/.ssh/id_ed25519.pub \
  --ask-vault-pass
```

`-e ansible_port=22` — текущий порт подключения; порт sshd всегда `22334`. Шаги и порт, который остаётся рабочим:

1. Проверка нового входа на 22. Ничего не изменено; при ошибке запуск останавливается.
2. Запуск создаёт уникальный идентификатор операции. Под блокировкой `/run/npv-sshd-rollback.lock` он создаёт `/etc/ssh/npv-sshd.rollback/` (это не удаётся, если каталог уже есть) и записывает `id` (владельца), затем `dropin` (копию текущего файла роли) или `absent` (файла не было), затем `complete` и в конце маркер `/run/npv-sshd-rollback.armed` с тем же идентификатором. Затем на 600 с запускается временный `npv-sshd-rollback-<ID>.timer`. Подготовка, каждое продвижение, отмена и откат выполняются под этой блокировкой и действуют, только если `id`, а для продвижения и отмены ещё и маркер, содержат их собственный идентификатор. Откат сначала удаляет маркер, восстанавливает `dropin` (или удаляет файл роли, если есть `absent`), перезагружает sshd и только после этого останавливает свой таймер и удаляет `id` и каталог. Если восстановление или reload не удались, `id` и снимок остаются, и та же операция может повторить откат; без `complete` ничего не продвигалось, поэтому откат только удаляет состояние. Команды с управляющей машины ждут блокировку до 60 с; откат по таймеру ждёт её без ограничения.
3. Кандидат с `Port 22` и `Port 22334` и полной политикой записывается в `/etc/ssh/npv-sshd.candidate.<ID>.conf`, вне `sshd_config.d`. Составной основной файл — `sshd_config`, в котором первый `Include` заменён кандидатом и остальными drop-in в порядке glob, — проверяется `sshd -t -f` и `sshd -T -f`. Только затем кандидат этой операции переименовывается поверх рабочего файла роли и выполняется reload `ssh.service` — одной командой, которая завершается ошибкой, если маркер не содержит идентификатор этой операции. Порты 22 и 22334 открыты с новой политикой; существующие сеансы продолжаются.
4. Проверяются команда root и SFTP на 22334. При ошибке, например если провайдер блокирует 22334, откат этой операции сразу выполняется через ещё открытый порт 22 и после успешного восстановления останавливает её таймер, а запуск завершается ошибкой с указанием шага. Порт 22 работает как прежде.
5. Итоговый кандидат (только `Port 22334`) так же проверяется и продвигается; reload выполняется через текущее подключение и закрывает 22. Команда root и SFTP проверяются на 22334 ещё раз.
6. Через новые подключения к 22334: `sshd -T` должен показать политику и только порт 22334, `ss` — что sshd слушает только TCP 22334 и на 22 ничего нет. Затем отмена, только если маркер и `id` всё ещё содержат идентификатор этой операции, удаляет маркер, `id` и каталог и останавливает таймер этой операции; иначе она завершается ошибкой, потому что откат уже начался или хост перезагрузился и проверенное состояние может быть уже не рабочим. Если ошибка случилась после шага 5, запуск сообщает, где он остановился; таймер через 600 с после запуска восстанавливает прежнюю конфигурацию и снова открывает 22. Не запускайте роль повторно, пока существует `/etc/ssh/npv-sshd.rollback`.

После итогового продвижения все задачи (проверки, итоговая проверка, отмена) выполняются на управляющей машине с `delegate_to: localhost` и подключаются через `ssh -p 22334` или `sftp -P 22334`, поэтому `-e ansible_port=22` на них не влияет. После шага 6 роль сообщает о переносе и завершает плейбук для этого хоста (`meta: end_host`): `-e ansible_port=22` имеет наивысший приоритет, поэтому запуск не может переключиться на 22334, и ни одна задача не должна заново подключаться к закрытому порту. Последующие роли плейбука для хоста пропускаются, а последующие плейбуки того же запуска попытались бы подключиться к порту 22. Следующий запуск без `-e ansible_port` использует порт инвентаря `22334`.

Обычная работа на 22334. На хосте, который уже доступен на 22334, например настроенном вручную, роль применяет политику сразу: проверка на 22334, таймер, файл роли, проверки, reload, проверки команды и SFTP, итоговая проверка и отмена таймера — всё на 22334; порт 22 не открывается. Любая ошибка, в том числе на итоговой проверке, сразу откатывается через подключение Ansible, а если это невозможно — таймером. Если текст файла роли уже актуален, запуск не открывает проверочных подключений и не выполняет reload; он лишь устанавливает файлу роли `root:root 0644`, если владелец, группа или режим отличаются (это предсказывается и с `--check`), и завершается успешно, только если `sshd -T` показывает политику с ровно `root` и портом `22334`, а `ss` — что sshd слушает только TCP 22334; иначе он завершается ошибкой с указанием расхождения.

Восстановление. До успешной отмены путём восстановления служит таймер. Если он срабатывает, пока запуск ещё работает, его откат ждёт блокировку, поэтому продвижение, которое выполняет reload sshd, сначала завершается; затем откат удаляет маркер, так что следующее продвижение этого запуска завершается ошибкой, не меняя файл роли, и отмена тоже не проходит: запуск никогда не сообщает об успехе для состояния, которое откат мог заменить. Устаревший запуск, таймер или rescue не может действовать за более позднюю операцию: каждое действие проверяет свой идентификатор под блокировкой, а кандидат и таймер содержат его в имени. Если управляющая машина потеряна после итогового reload, работающий sshd слушает только 22334, а таймер через 600 с после запуска восстанавливает прежний файл роли и снова открывает 22 (`systemctl list-timers 'npv-sshd-rollback*'`). Восстановление задерживается, пока блокировку держит другой участник (не дольше `systemctl reload`), и не происходит при перезагрузке, остановленном таймере или неудачном reload; результат — в `journalctl -u npv-sshd-rollback-<ID>.service`. Перезагрузка удаляет таймер и маркер. Непродвинутый кандидат sshd не читает, поэтому хост загружается с прежним файлом роли. Продвинутый файл роли проверен в составной конфигурации, но вход с ним мог быть ещё не проверен, и после перезагрузки его ничто не откатывает. `/etc/ssh/npv-sshd.rollback` остаётся и останавливает следующий запуск с такими указаниями: без `complete` ничего не продвигалось — удалите каталог и маркер; иначе либо восстановите `dropin` через `cp -p` (или удалите файл роли, если есть `absent`), выполните `sshd -t` и `systemctl reload ssh` и проверьте второй вход, либо оставьте текущий файл роли, проверив вход на каждом порту, который показывает `sshd -T`; затем удалите каталог, маркер и `/etc/ssh/npv-sshd.candidate.*`. Последнее средство — консоль провайдера, она вне этой роли.

Проверка и diff: с `--check` на порту 22 или 22334 роль выполняет ту же проверку только для чтения и останавливается на тех же препятствиях, показывает итоговый файл роли как diff (ключей в нём нет) и перечисляет запланированные шаги. Она ничего не записывает, не запускает таймер, не выполняет reload и не открывает проверочных подключений; проверки входа, проверки составного кандидата через `sshd -t -f`/`sshd -T -f`, reload, проверки команды и SFTP на 22334 и проверка прослушиваемых портов указываются как отложенные до обычного запуска.

Ограничения: доверие читается только из `~/.ssh/known_hosts`; `ansible_host` должен быть именем хоста или адресом IPv4; проверки показывают, что работает ключ проверки, а не каждый одобренный ключ.

## Планируемые плейбуки

Ни один из этих плейбуков пока не существует:

- `new_server.yml` — базовая настройка ОС на всех управляемых хостах.
- Отдельный плейбук для ingress-узлов (имя пока не выбрано).
- Отдельный плейбук для egress-узлов (имя пока не выбрано).

## Секреты

Секреты хранятся в Ansible Vault и никогда не коммитятся в открытом виде.
